1. 架构概览
================================================================================

核心设计: 链表式订单簿 (Doubly-linked list order book)
  - 使用 RocksDB 存储
  - 基于数组索引实现链表 (prev_order/next_order: u16)
  - 最大容量: 65535 (u16::MAX)
  - 每个 (mint, direction) 对应一个独立管理器

关键特性:
  - 多重索引: slot、id_map、user_active、closed_orders
  - WriteBatch 原子批操作
  - Mutex 序列化 insert/delete 操作
  - RocksDB 快照保证查询一致性

================================================================================
2. 数据结构
================================================================================

OrderBookHeader (64 bytes)
  - order_id_counter: u64 (全局单调递增)
  - head/tail: u16 (链表头尾索引)
  - total: u16 (有效索引范围: [0, total))
  - total_capacity: u32 (应等于 total)

MarginOrder (200+ bytes)
  - 用户/订单信息: user, order_id, order_type
  - 价格信息: open_price, lock_lp_start_price, lock_lp_end_price
  - 保证金和借款: margin_sol_amount, borrow_amount, borrow_fee
  - 仓位信息: position_asset_amount, lock_lp_sol_amount, lock_lp_token_amount
  - 时间信息: start_time, end_time
  - 链表指针: next_order, prev_order (u16, MAX=无)
  - 版本控制: version (更新时递增)

RocksDB 键设计:
  orderbook_slot:{mint}:{direction}:{index:05} → MarginOrder
  orderbook_id_map:{mint}:{direction}:{order_id:010} → index
  orderbook_user:{user}:{mint}:{direction}:{start_time:010}:{order_id:020} → ""
  orderbook_user_closed:{user}:{close_timestamp:010}:{mint}:{direction}:{order_id:020} → ClosedOrderRecord

================================================================================
3. 订单操作
================================================================================

插入 (insert_after / insert_before)
  1. 获取操作锁
  2. 加载 header 验证容量
  3. 处理空链表/正常插入
  4. WriteBatch 批量构建:
     - 写入订单槽位
     - 更新 ID 映射
     - 添加用户索引
     - 更新前驱/后继指针
     - 更新 header
  5. 原子提交

删除 (batch_remove_by_indices_unsafe)
  1. 获取操作锁
  2. 克隆、去重、降序排序索引
  3. 构建 HashMap 缓存 (← BUG!)
  4. 循环删除 (从大到小):
     - 从链表摘除节点
     - 删除 ID 映射和用户索引
     - 保存关闭记录
     - 移动末尾节点到删除位置
     - virtual_tail 前移
  5. 修复 tail 指针 (← 依赖缓存,可能不完整)
  6. 更新活跃索引列表
  7. 原子提交

更新 (update_order)
  - 不获取操作锁 (← 并发风险!)
  - 验证 order_id 双重检查
  - 选择性更新字段
  - 版本号递增

遍历 (traverse)
  - 支持分页和续传
  - 回调函数模式
  - 链表遍历

================================================================================
4. 并发控制机制
================================================================================

操作锁 (Mutex)
  - 保护: insert_after, insert_before, batch_remove_by_indices_unsafe
  - 不保护: update_order, traverse, get_order (← 风险!)
  位置: src/orderbook/manager.rs:37-40

WriteBatch 原子性
  - 优点: 多键原子提交
  - 限制: 无行级隔离,无跨批同步
  - 读操作可能看到中间状态

RocksDB 快照
  - 用于查询: UserOrderQueryService (L45)
  - 所有读操作在一致性视图上进行
  - 仅保护查询,不保护修改

序列化事件处理
  - 位置: src/solana/storage_handler.rs:85-183
  - 模式: spawn_blocking 任务
  - 步骤1: OrderBook 操作 (获取锁)
  - 步骤2: 价格更新 (无锁)
  - 目的: 删除时获取"删除前"价格,避免竞态条件

5. 已知问题和竞态条件
================================================================================

P0 严重: 批量删除中的缓存污染
  位置: src/orderbook/manager.rs:698-710
  问题: HashMap 缓存存储已被移动的订单
       再次读取时导致重复移动和订单丢失
  
  场景: 删除 [8, 5, 2] (total=10)
    - 删除8: 移动 order[9]→order[8], cache[8]=order[9]
    - 删除5: 读取 cache[8], 得到 order[9], 再移动到5
             order[8] 原始内容永远丢失 ✗
    - 删除2: 类似问题

  影响: 所有批量删除, 特别是接近末尾的多个删除
  概率: 低(需特定序列), 但在 10万+ 交易时累积增加
  
  验证: src/orderbook/tests/delete_test.rs:18 (被 #[ignore] 标记)
       test_delete_single_order_from_middle() - 删除 [2,3] 时触发

P1 中等: 缺乏更新操作的并发保护
  问题: update_order 不获取操作锁
  风险: 并发 update + delete 导致不一致
  例子: update 修改 order[5] 时, delete 可能同时删除它

P2 中等: tail 指针修复不完整
  位置: src/orderbook/manager.rs:907-957
  问题: 修复依赖缓存,可能读到已修改数据
        防止无限循环检查不充分
  结果: tail 指针指向无效位置,遍历失败

P3 低风险: 用户索引的时序不一致
  问题: 删除订单后,末尾订单被移动到该位置
       但末尾订单的用户索引也被删除了 (同批操作)
  结果: 订单在新位置,但用户索引丢失
       查询用户订单时找不到

6. 风险评估
================================================================================

影响范围                         严重度    概率      范围
缓存污染导致错删                P0 红     低        全局
并发更新冲突                    P1 黄    中        单订单
tail 指针错误                   P2 黄    低        遍历
用户索引丢失                    P3 橙    很低      用户查询

触发条件 (缓存污染 Bug):
  1. 删除多个索引接近末尾的订单
  2. 删除顺序为降序排列
  3. 循环中第 N 次删除读到第 N-1 次缓存
  4. 在 10万+ 交易压力下概率增加

10. 总结
================================================================================

OrderBook 模块采用复杂的"链表+数组混合"设计,以支持高效删除和重排。
然而,批量删除时的 HashMap 缓存管理存在严重缺陷,会导致订单被错误
删除或遗漏。这种问题在高并发场景(10万+ 交易)下触发概率增加。

核心问题:      缓存污染 + 指针重排的复杂交互
影响范围:      全局 OrderBook 数据完整性
优先级:        P0 (需要立即修复)
难度:          中等 (需要重构删除逻辑)

推荐方案:      
  1. 禁用有缺陷的缓存机制
  2. 使用 RocksDB 快照保证一致性
  3. 增加并发保护
  4. 启用并修复被忽略的单元测试
