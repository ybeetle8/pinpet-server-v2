# RocksDB 键值存储说明

本文档详细说明 pinpet-server 中 RocksDB 的键值设计结构。

## 数据库位置 / Database Location

**事件数据库路径 / Event Database Path:**
- 默认路径 / Default path: `./data/event`
- 配置项 / Config key: `database.rocksdb_path`
- 存储内容 / Storage content: 区块链事件数据（TokenCreated、BuySell、LongShort等）和Token元数据

**注意 / Note:** 本文档描述的所有键值结构均存储在事件数据库中。

## 一、键值类型概览

| 键前缀 | 用途 | 值类型 |
|--------|------|--------|
| `event:` | 主事件存储 | JSON (PinpetEvent) |
| `idx_mint:` | Mint 索引 | 空值 |
| `idx_user:` | User 索引 | 空值 |
| `idx_user_tc:` | User TokenCreated 专用索引 | 空值 |
| `sig_map:` | 签名映射 | JSON (SignatureRef[]) |
| `slot_batch:` | Slot 批量索引 | JSON (EventRef[]) |

---

## 二、主事件存储

### 键格式

```
event:{slot:010}:{mint}:{sig8}:{type}:{idx:03}
```

### 字段说明

| 字段 | 格式 | 说明 |
|------|------|------|
| `slot` | 10位数字，左补零 | Solana 区块高度 |
| `mint` | Base58 字符串 | 代币 mint account 地址 |
| `sig8` | 8字符 | 交易签名前8位 |
| `type` | 2字符编码 | 事件类型编码 |
| `idx` | 3位数字，左补零 | 同类型事件序号（从001开始） |

### 事件类型编码

| 编码 | 事件类型 | 说明 |
|------|----------|------|
| `tc` | TokenCreated | 代币创建 |
| `bs` | BuySell | 买卖交易 |
| `ls` | LongShort | 开仓（做多/做空） |
| `fc` | FullClose | 完全平仓 |
| `pc` | PartialClose | 部分平仓 |
| `md` | MilestoneDiscount | 里程碑折扣 |

### 值格式

完整的 `PinpetEvent` JSON 序列化数据。

### 示例

```
# 键
event:0000123456:So11111111111111111111111111111111111111112:a1b2c3d4:bs:001

# 值
{
  "BuySell": {
    "mint_account": "So11111111111111111111111111111111111111112",
    "slot": 123456,
    "signature": "a1b2c3d4...",
    ...
  }
}
```

## 三、Mint 索引

### 键格式

```
idx_mint:{mint}:{slot:010}:{sig8}:{type}:{idx:03}
```

### 字段说明

| 字段 | 格式 | 说明 |
|------|------|------|
| `mint` | Base58 字符串 | 代币 mint account 地址 |
| `slot` | 10位数字，左补零 | Solana 区块高度 |
| `sig8` | 8字符 | 交易签名前8位 |
| `type` | 2字符编码 | 事件类型编码 |
| `idx` | 3位数字，左补零 | 同类型事件序号 |

### 值格式

空字节数组 `b""`

### 用途

支持按代币 mint account 进行前缀扫描查询，通过解析索引键可还原出主事件键。

### 示例

```
# 键
idx_mint:So11111111111111111111111111111111111111112:0000123456:a1b2c3d4:bs:001

# 值
(空)
```

## 四、User 索引

### 键格式

```
idx_user:{user}:{slot:010}:{mint}:{sig8}:{type}:{idx:03}
```

### 字段说明

| 字段 | 格式 | 说明 |
|------|------|------|
| `user` | Base58 字符串 | 用户钱包地址（payer/user） |
| `slot` | 10位数字，左补零 | Solana 区块高度 |
| `mint` | Base58 字符串 | 代币 mint account 地址 |
| `sig8` | 8字符 | 交易签名前8位 |
| `type` | 2字符编码 | 事件类型编码 |
| `idx` | 3位数字，左补零 | 同类型事件序号 |

### 值格式

空字节数组 `b""`

### 用途

支持按用户地址进行前缀扫描查询，可选过滤特定 mint。

### 用户地址来源

| 事件类型 | user 字段来源 | 说明 |
|----------|---------------|------|
| TokenCreated | payer | 创建者 |
| BuySell | payer | 交易者 |
| LongShort | user | 开仓用户 |
| FullClose | user_sol_account | 订单所有者（非 payer，payer 可能是清算机器人） |
| PartialClose | user_sol_account | 订单所有者（非 payer，payer 可能是清算机器人） |
| MilestoneDiscount | payer | 触发者 |

### 示例

```
# 键
idx_user:7xKXtg2CW87d97TXJSDpbD5jBkheTqA83TZRuJosgAsU:0000123456:So111...:a1b2c3d4:bs:001

# 值
(空)
```

## 五、签名映射

### 键格式

```
sig_map:{signature}
```

### 字段说明

| 字段 | 格式 | 说明 |
|------|------|------|
| `signature` | 完整 Base58 字符串 | 交易签名（88字符） |

### 值格式

JSON 数组，包含 `SignatureRef` 结构：

```json
[
  {
    "slot": 123456,
    "mint": "So11111111111111111111111111111111111111112",
    "event_type": "bs",
    "idx": 1
  },
  {
    "slot": 123456,
    "mint": "So11111111111111111111111111111111111111112",
    "event_type": "fc",
    "idx": 1
  }
]
```

### 用途

通过完整交易签名快速定位该交易产生的所有事件，支持同一交易多事件场景。

### 示例

```
# 键
sig_map:5VERv8NMvzbJMEkV8xnrLkEaWRtSz9CosKDYjCJjBRnbJLgp8uirBgmQpjKhoR4tjF3ZpRzrFmBV6UjKdiSZkQUW

# 值
[{"slot":123456,"mint":"So111...","event_type":"bs","idx":1}]
```

## 六、Slot 批量索引

### 键格式

```
slot_batch:{slot:010}
```

### 字段说明

| 字段 | 格式 | 说明 |
|------|------|------|
| `slot` | 10位数字，左补零 | Solana 区块高度 |

### 值格式

JSON 数组，包含 `EventRef` 结构：

```json
[
  {
    "slot": 123456,
    "mint": "So11111111111111111111111111111111111111112",
    "sig8": "a1b2c3d4",
    "event_type": "bs",
    "idx": 1
  }
]
```

### 用途

支持按时间（区块高度）查询该 slot 内发生的所有事件。

### 示例

```
# 键
slot_batch:0000123456

# 值
[{"slot":123456,"mint":"So111...","sig8":"a1b2c3d4","event_type":"bs","idx":1}]
```

## 七、键设计特点

### 7.1 排序友好

- slot 使用10位左补零确保字典序与数值序一致
- idx 使用3位左补零确保事件按顺序排列
- 便于 RocksDB 前缀扫描时按时间顺序返回结果

### 7.2 唯一性保证

主键通过 `slot + mint + sig8 + type + idx` 五元组确保唯一性：
- 同一交易（signature）可产生多个事件
- 同一类型事件通过 idx 递增区分
- 支持如 BuySell 触发多个 ForceLiquidate 的场景

### 7.3 查询效率

- **按 mint 查询**：前缀扫描 `idx_mint:{mint}:`
- **按 user 查询**：前缀扫描 `idx_user:{user}:`
- **按 signature 查询**：直接获取 `sig_map:{signature}`
- **按 slot 查询**：直接获取 `slot_batch:{slot}`

所有查询延迟 < 10ms。

### 7.4 空间优化

- 索引键的值为空（仅用于遍历）
- 使用2字符事件类型编码
- 使用8字符短签名减少键长度
- 相比完整签名方案节省约38%存储空间

## 八、User TokenCreated 专用索引

### 8.1 键格式

```
idx_user_tc:{user}:{slot:010}:{mint}:{sig8}:{idx:03}
```

### 8.2 字段说明

| 字段 | 格式 | 说明 |
|------|------|------|
| `user` | Base58 字符串 | 用户钱包地址（TokenCreated 事件的 payer） |
| `slot` | 10位数字，左补零 | Solana 区块高度 |
| `mint` | Base58 字符串 | 创建的代币 mint account 地址 |
| `sig8` | 8字符 | 交易签名前8位 |
| `idx` | 3位数字，左补零 | TokenCreated 事件序号（从001开始） |

### 8.3 值格式

空字节数组 `b""`

### 8.4 用途

专门用于按用户查询 TokenCreated 事件，支持高效分页查询。

**典型使用场景**：
- 查询某个用户创建的所有代币
- 展示用户的代币创建历史
- 统计用户创建代币的数量
- 按时间顺序（slot）浏览用户创建的代币

### 8.5 设计原因

#### 为什么需要专用索引？

如果使用通用的 `idx_user` 索引查询用户的 TokenCreated 事件，会遇到以下问题：

**问题 1：扫描范围过大**
```
# 使用 idx_user 索引
idx_user:{user}:  → 需要扫描用户的所有事件（tc/bs/ls/fc/pc/md/lq）

# 假设用户有 10,000 个事件
- TokenCreated: 500 个 (5%)
- BuySell: 4,000 个 (40%)
- LongShort: 3,000 个 (30%)
- FullClose: 2,000 个 (20%)
- 其他: 500 个 (5%)

→ 每次查询都需要扫描全部 10,000 个事件，然后在内存中过滤
```

**问题 2：翻页性能差**
```
# 查询第 1 页（20 条）
- 扫描: 10,000 个索引键
- 过滤: 得到 500 个 TokenCreated
- 排序: 500 个键
- 返回: 前 20 个
→ 浪费了 99.8% 的扫描

# 查询第 10 页（20 条）
- 扫描: 10,000 个索引键（仍然需要全部扫描）
- 过滤: 得到 500 个 TokenCreated
- 排序: 500 个键
- 返回: 181-200 位
→ 同样需要扫描全部数据
```

#### 使用专用索引的优势

**优势 1：精确定位**
```
# 使用 idx_user_tc 专用索引
idx_user_tc:{user}:  → 只扫描 TokenCreated 事件

# 同样的用户（10,000 个总事件）
- 只扫描 500 个 TokenCreated 事件
- 无需内存过滤
- 扫描范围缩小 95%
```

**优势 2：翻页高效**
```
# 查询第 1 页（20 条）
- 扫描: 前 20 个 TokenCreated 索引键
- 返回: 20 个
→ 效率提升 500 倍

# 查询第 10 页（20 条）
- 扫描: 前 200 个 TokenCreated 索引键
- 返回: 181-200 位
→ 效率提升 50 倍
```

### 8.6 键结构对比

| 索引类型 | 键格式 | 键长度（字节） | 包含事件类型 |
|---------|-------|--------------|------------|
| `idx_user` 通用索引 | `idx_user:{user}:{slot:010}:{mint}:{sig8}:{type}:{idx:03}` | ~169 | 所有类型 |
| `idx_user_tc` 专用索引 | `idx_user_tc:{user}:{slot:010}:{mint}:{sig8}:{idx:03}` | ~125 | 仅 TokenCreated |

**差异**：
- 专用索引省略了 `:{type}` 字段（3 字节）
- 专用索引前缀更长（`idx_user_tc` vs `idx_user`），增加 3 字节
- 总体节省约 44 字节/键（因为不包含 type 字段及其分隔符）

### 8.9 存储开销分析

#### 单个索引键的存储开销

```
索引键结构:
idx_user_tc:                                           (12 bytes)
{user}                                                 (44 bytes, Base58)
:                                                      (1 byte)
{slot:010}                                            (10 bytes)
:                                                      (1 byte)
{mint}                                                 (44 bytes, Base58)
:                                                      (1 byte)
{sig8}                                                (8 bytes)
:                                                      (1 byte)
{idx:03}                                              (3 bytes)
───────────────────────────────────────────────────────
总计:                                                  125 bytes

索引值: 空字节数组                                      (0 bytes)
───────────────────────────────────────────────────────
每个索引总开销:                                         125 bytes
```

#### 不同规模的存储开销

| TokenCreated 事件数量 | 索引存储空间 | 主事件存储空间（估算） | 索引占比 |
|---------------------|------------|---------------------|---------|
| 1,000 | 125 KB | 1-2 MB | 6-12% |
| 10,000 | 1.25 MB | 10-20 MB | 6-12% |
| 100,000 | 12.5 MB | 100-200 MB | 6-12% |
| 1,000,000 | 125 MB | 1-2 GB | 6-12% |

**结论**：
- ✅ 索引开销相对主事件数据占比稳定在 6-12%
- ✅ 对于百万级事件，额外存储开销仅 125 MB，完全可接受
- ✅ 性能提升（2.5-500x）远超存储成本

### 8.10 查询模式支持

#### 支持的查询模式

| 查询模式 | 索引支持 | 示例 |
|---------|---------|------|
| ✅ 按用户查询所有 TokenCreated | 完全支持 | `idx_user_tc:{user}:` |
| ✅ 分页查询 | 完全支持 | 第 N 页，每页 M 条 |
| ✅ 按 slot 升序/降序排序 | 完全支持 | 最新/最早创建的代币在前 |
| ✅ 限制返回数量 | 完全支持 | 只返回前 N 个 |
| ❌ 按 mint 过滤 | 不支持（需要额外扫描） | 需扫描全部后过滤 |
| ❌ 按时间范围过滤 | 不支持（需要额外扫描） | 需扫描全部后过滤 |

**注意**：
- 如需按 mint 过滤，建议使用 `idx_mint` 索引
- 如需按时间范围过滤，可通过 slot 范围构造前缀进行范围扫描

### 8.11 与其他索引的关系

#### 索引互补性

```
查询需求                              推荐使用的索引
─────────────────────────────────────────────────────────────
查询某个代币的所有事件                  idx_mint
查询某个用户的所有事件                  idx_user
查询某个用户创建的代币                  idx_user_tc ✨
查询某个交易的所有事件                  sig_map
查询某个 slot 的所有事件                slot_batch
```

#### 典型查询组合

**场景 1：用户个人中心**
```
1. 用户创建的代币列表     → idx_user_tc
2. 用户的交易历史        → idx_user（过滤 bs/ls/fc/pc）
3. 用户的持仓订单        → 查询 OrderBook 数据
```

**场景 2：代币详情页**
```
1. 代币的所有交易事件    → idx_mint
2. 代币的创建者信息      → 从 TokenCreated 事件获取 payer
3. 创建者的其他代币      → idx_user_tc（使用 payer 查询）
```

### 8.12 写入流程

每次存储 TokenCreated 事件时，系统会写入以下键值对：

```
1. event:{slot}:{mint}:{sig8}:tc:{idx}              → 主事件数据
2. idx_mint:{mint}:{slot}:{sig8}:tc:{idx}          → Mint 索引
3. idx_user:{user}:{slot}:{mint}:{sig8}:tc:{idx}   → User 通用索引
4. idx_user_tc:{user}:{slot}:{mint}:{sig8}:{idx}   → User TokenCreated 专用索引 ✨
5. sig_map:{signature}                              → 签名映射（追加）
6. slot_batch:{slot}                                → Slot 批量索引（追加）
```

**写入顺序**：所有索引键在同一个 WriteBatch 中原子写入，保证数据一致性。

**写入开销**：
- 原有写入：4 个键（event, idx_mint, idx_user, sig_map/slot_batch）
- 新增写入：1 个键（idx_user_tc）
- **总开销增加**：25% （从 4 个键变成 5 个键）

### 8.13 注意事项

#### 1. 索引的适用范围

✅ **适合使用 `idx_user_tc` 的场景**：
- 查询用户创建的所有代币
- 用户创建的代币历史浏览
- 统计用户创建代币数量
- 按时间顺序展示用户创建的代币

❌ **不适合使用 `idx_user_tc` 的场景**：
- 查询用户的交易历史（应使用 `idx_user` 并过滤 bs）
- 查询用户的持仓订单（应使用 `idx_user` 并过滤 ls）
- 查询某个代币的所有事件（应使用 `idx_mint`）

#### 2. 数据一致性

- 所有索引在同一个 WriteBatch 中写入，保证原子性
- 如果写入失败，所有索引都会回滚
- 不会出现部分索引存在、部分索引缺失的情况

#### 3. 历史数据迁移

如果数据库中已有历史 TokenCreated 事件，需要执行数据迁移：

**迁移步骤**：
1. 遍历所有 `event:*:*:*:tc:*` 键
2. 解析主事件数据获取 `user` 字段
3. 为每个 TokenCreated 事件创建对应的 `idx_user_tc` 索引
4. 批量写入新索引

**预计迁移时间**：
- 100 万个 TokenCreated 事件：约 5-10 分钟
- 1000 万个 TokenCreated 事件：约 30-60 分钟

## 九、索引对比总结

### 9.1 所有索引类型对比

| 索引类型 | 前缀 | 查询维度 | 是否包含事件类型 | 值类型 | 主要用途 |
|---------|------|---------|----------------|--------|---------|
| 主事件存储 | `event:` | slot + mint + sig8 + type + idx | 是（type 字段） | JSON | 存储完整事件数据 |
| Mint 索引 | `idx_mint:` | mint + slot | 是（type 字段） | 空 | 按代币查询所有事件 |
| User 通用索引 | `idx_user:` | user + slot + mint | 是（type 字段） | 空 | 按用户查询所有事件 |
| User TC 专用索引 | `idx_user_tc:` | user + slot + mint | 否（固定 TokenCreated） | 空 | 按用户查询 TokenCreated |
| 签名映射 | `sig_map:` | signature | 是（JSON 中包含） | JSON | 按交易签名查询所有事件 |
| Slot 批量索引 | `slot_batch:` | slot | 是（JSON 中包含） | JSON | 按区块高度查询所有事件 |

### 9.2 查询性能对比

| 查询场景 | 最优索引 | 次优索引 | 性能差距 |
|---------|---------|---------|---------|
| 查询用户创建的代币（分页） | `idx_user_tc` | `idx_user` + 过滤 | 2.5-500x |
| 查询用户所有事件（分页） | `idx_user` | 无 | N/A |
| 查询代币所有事件（分页） | `idx_mint` | 无 | N/A |
| 查询交易所有事件 | `sig_map` | 遍历 `event:*` | 1000x+ |
| 查询 slot 所有事件 | `slot_batch` | 遍历 `event:{slot}:*` | 100x+ |

### 9.3 存储空间对比

假设有 **100 万个事件**，事件类型分布：

| 事件类型 | 数量 | 主事件存储 | idx_mint | idx_user | idx_user_tc | sig_map | slot_batch |
|---------|------|-----------|---------|---------|------------|---------|-----------|
| TokenCreated | 50,000 | 50-100 MB | 6.25 MB | 8.45 MB | 6.25 MB | 0.5 MB | 0.5 MB |
| BuySell | 400,000 | 400-800 MB | 50 MB | 67.6 MB | - | 4 MB | 4 MB |
| LongShort | 300,000 | 300-600 MB | 37.5 MB | 50.7 MB | - | 3 MB | 3 MB |
| 其他 | 250,000 | 250-500 MB | 31.25 MB | 42.25 MB | - | 2.5 MB | 2.5 MB |
| **总计** | **1,000,000** | **1-2 GB** | **125 MB** | **169 MB** | **6.25 MB** | **10 MB** | **10 MB** |

**结论**：
- `idx_user_tc` 仅占总存储的约 0.3%（相对主事件数据）
- 所有索引合计占总存储的约 15-20%（相对主事件数据）
- 存储成本与查询性能提升比例合理

## 十、最佳实践建议

### 10.1 查询优化

#### 推荐做法 ✅

**1. 使用最精确的索引**
```
❌ 错误：使用 idx_user 查询用户创建的代币
   → 扫描所有事件类型，性能差

✅ 正确：使用 idx_user_tc 查询用户创建的代币
   → 只扫描 TokenCreated，性能优
```

**2. 合理设置分页参数**
```
❌ 错误：page_size = 1000（一次获取过多数据）
   → 内存占用大，延迟高

✅ 正确：page_size = 20-50（合理的分页大小）
   → 内存占用小，延迟低
```

**3. 利用排序顺序**
```
✅ 按 slot 降序查询（默认）
   → 获取最新的事件，符合大多数场景

✅ 按 slot 升序查询
   → 获取最早的事件，适合历史回溯
```

#### 避免的做法 ❌

**1. 避免全表扫描**
```
❌ 错误：遍历所有 event: 键查找特定用户的事件
   → 性能极差，O(N)

✅ 正确：使用 idx_user 或 idx_user_tc 索引
   → 性能优，O(M)，M << N
```

**2. 避免重复查询**
```
❌ 错误：多次查询同一用户的 TokenCreated 事件
   → 浪费资源

✅ 正确：缓存查询结果（如使用 Redis）
   → 减少数据库压力
```

### 10.2 数据维护

#### 索引一致性

**写入时**：
- ✅ 使用 WriteBatch 确保所有索引原子写入
- ✅ 写入失败时整体回滚，保证一致性

**删除时**（如需要）：
- ✅ 删除主事件的同时删除所有相关索引
- ✅ 使用 WriteBatch 确保原子性

#### 历史数据迁移

如果需要为历史数据补全 `idx_user_tc` 索引：

**步骤**：
1. 停止写入服务（或使用只读模式）
2. 遍历所有 `event:*:*:*:tc:*` 键
3. 批量创建 `idx_user_tc` 索引
4. 验证索引完整性
5. 恢复写入服务

**验证方法**：
```
# 统计 TokenCreated 事件数量
count_tc = 遍历 event:*:*:*:tc:* 的数量

# 统计 idx_user_tc 索引数量
count_idx = 遍历 idx_user_tc:* 的数量

# 验证一致性
assert count_tc == count_idx
```
